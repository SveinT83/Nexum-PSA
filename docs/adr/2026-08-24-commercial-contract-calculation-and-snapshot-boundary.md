# ADR: Commercial Contract Calculation And Customer Snapshot Boundary

Status: Accepted
Date: 2026-08-24
Decision Makers: Svein Tore, Codex

## Context

Commercial contract customer surfaces currently calculate and present the same line snapshots in
several different ways. Float arithmetic and mutable catalogue fallbacks can make UI, API, acceptance
evidence, and PDF disagree or drift after a contract is sent.

## Decision

Commercial owns one minor-unit pricing calculator and one customer-document projector.

The calculator accepts decimal strings from Contract line snapshots, converts them to integer minor
units, applies quantity and discounts with explicit half-up rounding, adds setup fees to one-time
amounts, and groups positive amounts by billing cadence. It exposes integer minor units plus canonical
decimal strings. Customer formatting never becomes a second calculation.

Sale currency is snapshotted independently on `ContractItem`; `cost_currency` is not sale-currency
evidence. The current customer Contract boundary is NOK-only. Authoritative Service/CloudFactory
currency is re-read on every line save, and non-NOK or tampered input fails before persistence.
CloudFactory Contract sale-price and markup projection also uses Brick decimal arithmetic and returns a
canonical two-decimal string; a binary float is not accepted as Contract-bound monetary input.

The projector accepts only contract-owned snapshot fields for commercial lines, descriptions, units,
rates, SLA/support text, and terms. Mutable Service, Time Rate, SLA, or company-catalogue values may be
used while composing an editable draft, but they are copied before use in a sent document.

A complete `contracts.customer_document_snapshot` is captured when a draft quote/agreement is sent or
manually approved. Sent and approved customer surfaces use that immutable projection. Null means
absent; every non-null JSON value is immutable evidence. Empty, scalar,
malformed, or unsupported-schema snapshots fail closed instead of rebuilding from live rows. The v1
reader validates the complete structural and typed envelope; `schema_version: 1` without the required
document, dates, parties, approval, exact ordered Norwegian six-column map, priced lines, four totals,
optional sections, and appendices is unsupported evidence. Redundant minor/decimal/display money
values must also agree semantically, including the exact `Inkludert` invariant; evidence is rejected,
not normalized or rewritten. Exact allowed-key and list-shape checks reject unknown internal/future
fields rather than exposing them through a shape-compatible response; strict JSON integer/boolean
checks prevent numeric strings from changing the typed API contract.

Legal review metadata version 2 binds two independent facts: the exact selected source term/version set
and the exact Contract snapshot text reviewed by the technician. Per-field source checksums identify
manual wording. Manually edited wording is captured verbatim as an `origin=contract` snapshot labelled
`Versjon 1 (kontraktsspesifikk)`, not as a mismatching catalogue version.

Every legacy sent/approved/won Contract without complete customer JSON fails closed on delivery,
acceptance, PDF, portal, public view, capture, and detail API. Current live rows cannot prove historical
party/economic facts. Tech may render only a marked read-only reconstruction aid. A named technician
may freeze it through a separate attestation action only after comparison with original evidence; the
audit binds a stable preview fingerprint and original document type, records actor, time, note, source
status, type, and snapshot hash, and never replaces non-null evidence. Ambiguous approved/won records
show no reconstruction before the technician chooses the type proven by the original. A blocked row in
the paginated admin API list is isolated with null document/pricing and explicit readiness metadata so
other rows remain available. Missing historical secure tokens are not regenerated by public/resend
paths. Terms `GET` is preview-only; refresh/save requires an explicit CSRF-protected `POST`, and removed
pre-metadata sources fail closed.

Bearer access belongs to one sent snapshot lifecycle. A new send rotates the token under the Contract
lock, resend retains that token, and manual approval of an editable unsent Contract clears any dormant
token so a previously shared link cannot cross a customer/snapshot boundary.

Internal SLA and rate relationships remain first-class Commercial data. Customer visibility for a rate
is an explicit catalogue field copied into the contract rate snapshot; no customer view performs
name-based filtering. Historical unknown visibility is classified before production and is never
inferred from a rate name, code, or operational use.

## Rationale

- Integer minor units meet the money-accuracy requirement without adding a new package.
- A single projector makes UI, API, snapshot, public preview, portal, and PDF parity testable.
- Capturing the presented document prevents later catalogue and branding edits from changing accepted
commercial evidence.
- Contract line snapshots preserve negotiated operational details while customer presentation can omit
internal implementation columns.
- Explicit visibility is auditable and safer than string heuristics.

## Consequences

- Commercial controllers and Livewire must request the shared projection instead of calculating totals.
- CloudFactory reconciliation that may change a won line must transact and lock the authoritative
  parent Contract before it resolves and locks that Contract-owned child.
- API responses add structured totals and customer-document data.
- Existing approved contracts are never backfilled from live catalogue text. Their missing descriptions
  appear only inside the blocked internal reconstruction aid; legacy rates without explicit snapshot
  visibility stay customer-hidden until an authoritative classification is reviewed.
- Term source changes or manual text changes invalidate metadata-v2 readiness until the exact result is
  reviewed and saved; the application does not silently refresh legal wording at send time.
- A non-null unsupported customer snapshot blocks read/capture rather than falling back.
- Setup fees become visible in the one-time summary even when attached to recurring lines.
- Quarterly legacy lines remain supported so positive amounts are never omitted, although the Service
  catalogue continues to offer monthly, yearly, and one-time defaults.
- The JSON snapshot is denormalized evidence and must not be edited through mass assignment.
- The first migration backfills editable descriptions in bounded id chunks. Its rollback fails while
  any customer snapshot, customer wording/unit, or visible-rate classification remains. The separate
  sale-currency migration preflights non-NOK source/offer values and refuses rollback of unsupported
  stored currencies. Export/verification and a separately approved cleanup are required first.

## Alternatives Considered

- Continue view-specific arithmetic: rejected because parity cannot be guaranteed.
- Use float plus rounding: rejected because binary floating-point is not an acceptable money boundary.
- Read current Service/rate text for old contracts: rejected because accepted output would drift.
